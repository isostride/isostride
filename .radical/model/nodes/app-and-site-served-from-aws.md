Then the runner asked: \"ok chce przeniesc wszystko na pipleline i miec poprawne ci/cd\", and chose for the test FIT files \"Prywatny bucket S3\". Asked to make the check faster (\"testwy trwaja dlugo ... mozesz je zrownoleglic na github ?\"), the runner agreed to its stages as jobs side by side (\"tak\"). Model's choices: the check on pull requests too, and the deploy taking the build the check made; the stages of the check as jobs side by side (unit and integration tests, the shuffled run, the end-to-end tests in three shards, the static checks), their reports handed to the verdict through the private test data bucket (ci/<run>/, gone after 3 days), never as public artifacts (but WebKit's one test, which reads none of the runner's files and runs in Playwright's image, its libraries there already); the browsers cached, the shards in Chromium only; the buckets in eu-central-1, private, read by CloudFront only (origin access control), versioned with old versions kept 30 days; one certificate in us-east-1 for the domain and *.domain; a CloudFront Function reading /run as run.html; HSTS and the usual security headers; hashed files cached a year, the rest checked on every visit; the deploy role taken by the workflow through GitHub OIDC, only from master, only able to replace the two buckets' files and clear the two caches; a second role, only able to read the test data bucket, taken from master and from pull requests of this repository; no reports, traces or screenshots published from the pipeline, as the repository and its logs are public; the Terraform state in its own bucket; the data's own names (the browser's keys) kept, so the data already made stays readable. On 26 Nov 2026 a merge was not deployed: after a green pull request, one end-to-end test that fails one time in many failed on master; the runner: \"chce aby ci/cd dzialal stabilnie ... jesli check przechodzi na branchu to pwinien przechodzic na merge do main\". Model's choices: master takes a pull request only when its branch is up to date and its check green, so the commit a merge leaves holds the very tree that check ran on; a check that passes (every job before the verdict too) marks the tree's hash in the test data bucket (ci/checked/<tree>, gone after 3 days like the reports); a push to master, or a run started by hand, of a marked tree runs no test again, builds the app and the site with that commit (the app shows its commit) and deploys them, so the build deployed is then made from the tree checked, not the very build the tests ran against; a tree without a mark is checked whole, its own build deployed, as before; a pull request is always checked whole, and its check fails rather than being left out when the job that asks for the mark fails."
