label: "A copy in the browser on phones"
alternatives: "The copy on every device: no gain where the folder is fast, and two copies of everything. The data in OPFS only, the folder as an export: against ADR \"Folder via File System Access\" (the runner's data visible and theirs). Filling the whole copy at once when the folder is opened: minutes on the phone before anything shows."
consequences: "On the phone a file read once is read from the copy afterwards, also in the next sessions, and the copy is filled in the background with what it lacks after the app opens (the runner's \"zrob a i b\"), so the screens soon stop waiting on the folder; the results the background jobs keep (derived/cache/) live in the copy alone, so a job no longer writes to the slow folder; every other write still takes the folder's time. The folder stays the whole data (but those kept results, made again when missing): the copy can be lost (site data cleared) and is filled again. A change to the runner's settings made outside this browser without a change of the data stamp is not seen until the copy is dropped. Desktops keep reading the folder alone."
context: "The data live in a folder the runner chooses (ADR \"Folder via File System Access\"). On Android, Chrome reaches that folder through the system's storage access: the runner's fast phone took 0.6–1 s for each call and ~3 s to read a file's content, whatever its size (a 2 KB index in 5 s); keeping what was read in memory (ADR \"One reading worker, files kept\") helps only once a file was read in this session, and every opening read each file again. The browser's private storage (OPFS) reads in milliseconds and holds as much as IsoStride writes (an origin may use about 60% of the disk), but it is invisible to the runner and may be cleared with the site's data."
date: "2026-11-24"
decision: "We will, on Android, keep a copy of the app's own files (.isostride/) in OPFS, one copy for each folder chosen: a file is read from the copy and, missing there, from the folder and put in the copy; a write goes to the folder, then to the copy; a removal removes from both; the FIT files and every listing come from the folder. When the app opens, the folder's data stamp is compared with the copy's, in the background; when they differ (the folder changed outside this browser) the next opening takes a new copy and the app is opened again. A copy is never removed under a page using it: the copies but the one in use are pruned in the background when the app opens. A copy that fails (removed, no room) is left for the session, the folder read alone, and the next opening takes a new one. A file found empty in the copy (a write cut off by a page left) is read from the folder and the copy mended. The workers read through the same copy."
status: "accepted"
